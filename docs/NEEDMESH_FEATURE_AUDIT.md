# NeedMesh feature audit

Audit of the realignment brief ("NeedMesh first, PromiseTwin second") against the code in this
repository, as of 10 Nov 2026. NeedMesh is the product; PromiseTwin is a protection capability built
into every NeedMesh purchase and also available as standalone purchase protection.

**Status legend**

- **Working**: implemented, deterministic, covered by unit tests and/or `smoke:*` / E2E scripts.
- **Working (simulated data)**: the code path is real, but the counterparty is a fictional demo
  merchant, the simulated PayPal rail or a simulated clock. Always labelled in the UI.
- **Partial**: a real subset exists; the gap is stated.
- **Not implemented**: a future path. Nothing in the UI claims it works.

Paths are relative to the repository root. `nm/` = `backend/src/modules/needmesh/`,
`fe/` = `frontend/src/`.

## Credentials and access not available in this environment

- PayPal Sandbox `PAYPAL_CLIENT_ID` / `PAYPAL_CLIENT_SECRET`: without them the **simulated rail** runs
  and every artifact is labelled Simulated.
- `PAYPAL_WEBHOOK_ID` and a publicly reachable URL for webhooks.
- PayPal MCP (`PAYPAL_MCP_ENABLED`) depends on the Sandbox credentials above.
- LLM keys (`OPENAI_API_KEY` / `GEMINI_API_KEY`): narration and parsing use the deterministic
  fixture provider.
- `CHANNEL3_API_KEY` and the Channel3 adapter itself.
- Real merchant onboarding or PayPal partner permissions: all merchants are fictional.

## What the product deliberately does not claim

No pooled wallet, escrow or charitable-donation status. No unrestricted splitting of PayPal
transactions. No autonomous spending: every payment action passes `mission-policy@1.0.0`, needs a
sponsor approval and, for captures, a merchant stock confirmation. A capture is never treated as
proof of delivery.
